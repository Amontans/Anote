# GUI 界面规划（GUI-PLAN）

> 目标：在**不破坏 Anote 核心原则**（薄壳/纯文本/低维护/轻量）的前提下，获得专业 GUI 体验。
> 约束回顾：8GB 老机器 + i3；本地优先、全开源、AI 仅经 Pi；数据契约冻结；任何 GUI 只是"新外壳"，services 仍是唯一真相。

## 〇、前提（先立规矩）
1. **GUI = 表现层**：调 `services/` + `anote` 命令，绝不复制业务逻辑（薄壳原则，否则维护爆炸）
2. **数据契约不变**：registry.md / src / memory / queue 格式冻结
3. **可随时弃用**：GUI 是"可替换外壳"，命令行永远可用

---

## 一、选项全景（四类 14 项）

### A 类：借用成熟软件当外壳（零开发或极小开发）

| 选项 | 做法 | 优点 | 缺点 | 工作量 |
|------|------|------|------|:---:|
| **A1 VS Code 扩展** | 写一个 VS Code 扩展（Anote 面板：文件树/命令/预览），调 `anote` CLI/MCP | 你已装 VS Code；零新重量；编辑器/终端/预览一体 | 局限在 VS Code 生态；VS Code 本身非轻量 | 中（几天） |
| A2 Obsidian 挂载 | 把 MD 部分（memory/registry/queue）作为 vault；TEX 笔记当文本 | 图谱/插件现成 | TEX 原生差；Electron 重；核心闭源；数据格式双轨 | 低 |
| A3 Joplin/Logseq | 同上思路 | 开源 | 同 TEX 短板；要迁移数据 | 低 |
| A4 Zotero | 文献 GUI 已有（已集成） | — | 只管文献，不管知识库 | 0 |

### B 类：自写 Web 应用（浏览器访问）★ 推荐方向

| 选项 | 做法 | 优点 | 缺点 | 工作量 |
|------|------|------|------|:---:|
| **B1 Web GUI（轻后端+模板）** | FastAPI/Flask + Jinja2 模板 + 少量 JS（或纯 stdlib http.server 增强） | 复用 services 最直接；浏览器=桌面+手机统一；移动端终于可用；轻量 | 交互流畅度 < SPA | **1-2 周 MVP** |
| **B2 Web GUI（SPA）** | FastAPI + Vue3/React 前端（API 驱动） | 体验最佳（图谱/拖拽/实时） | 工程量 ×2；前端依赖维护 | 1-2 月 |
| B3 静态站导出 | `anote export --html` 生成只读站点 | 发布/分享 | 非交互 GUI | 半天 |
| B4 Web 只读增强 | 现有 `anote web` 升级：加 registry/图谱/周报页 | 最小改动 | 交互仍弱 | 1 天 |

### C 类：自写桌面应用

| 选项 | 做法 | 优点 | 缺点 | 工作量 |
|------|------|------|------|:---:|
| C1 PySide6/PyQt | Qt 桌面应用（树/表格/编辑器组件全） | 原生桌面体验；与 i3 集成 | 依赖 Qt（~150MB）；只能桌面 | 2-4 周 |
| C2 Tkinter | stdlib | 零依赖 | 丑、控件老、维护体验差 | 中（不推荐） |
| C3 GTK(PyGObject) | Linux 原生 | 与系统一致 | API 繁琐；绑定维护 | 中高 |
| C4 Tauri/Electron | WebView 壳 | Tauri 轻量现代 | Tauri 要 Rust 工具链；Electron 在 8GB 上重 | 高 |

### D 类：增强现有（不算新 GUI）

| 选项 | 做法 | 优点 | 缺点 |
|------|------|------|------|
| D1 增强 TUI | Textual 已支持鼠标；补图表/图谱渲染 | 零新依赖；终端即 GUI | 仍是终端形态 |

## 二、决策维度（怎么选）

| 维度 | 权重 | 说明 |
|------|:---:|------|
| 维护成本 | ⭐⭐⭐ | 你反复强调"低维护"——GUI 每多一层依赖就多一份维护 |
| 轻量（8GB） | ⭐⭐⭐ | Electron 直接排除；Qt/Web 可接受 |
| 数据契约复用 | ⭐⭐⭐ | 必须走 services（薄壳） |
| 多端/移动 | ⭐⭐ | Web 天生多端；桌面只能本机 |
| 学习曲线 | ⭐ | 主要你一人用 |
| 工作量 | ⭐⭐ | MVP 越快见效越好 |

## 三、推荐方案（详述）

### 首选：B1 —— Web GUI（轻后端 + 服务端渲染）

**架构**（严格薄壳）：
```
浏览器(桌面/手机) ──HTTP──▶ anote-web(FastAPI/Flask)
                                   │ 调 services/（复用全部逻辑）
                                   └─ 数据目录（契约不变）
```

**页面规划**（与现有数据一一对应）：
| 页面 | 数据源 | 功能 |
|------|--------|------|
| 📚 文档库 | docs/registry.md | 表格+过滤排序、状态/进度一键更新、导入 |
| 📖 阅读器 | pdfs/ebooks + .txt | 内嵌 PDF(iframe)/epub 文本阅读、进度记录（读即登记复用） |
| 📝 笔记 | src/ | 学科树 + MD/TEX 渲染预览、编辑（跳转 $editor 或内嵌） |
| 🔍 检索 | RetrievalService | 混合检索结果面板（引用可点） |
| 🕸 图谱 | graph 数据 | 标签→笔记可视化（轻量 SVG/网络图） |
| 📥 队列/🧠 记忆/📚 书 | queue.md/memory/*.md/books | 视图（复用 TUI 页逻辑） |
| ⚙️ 设置 | Config | 数据目录（含迁移入口）、主题、reader |

**技术选型**：Flask（最简、维护低）或 FastAPI（自动文档、类型友好）。前端：Jinja2 模板 + 少量原生 JS（不引框架）→ 依赖面最小。加 `--token` 口令 + 仅 127.0.0.1（已有思路）。

**里程碑**：
| M | 内容 | 工作量 |
|---|------|:---:|
| G1 | Flask 骨架 + 文档库页（registry CRUD）+ 检索页 | 2-3 天 |
| G2 | 阅读器页（PDF 内嵌/epub 文本 + 进度） | 2 天 |
| G3 | 笔记树 + 预览 + 图谱页 | 2-3 天 |
| G4 | 队列/记忆/设置 + 安全打磨 + 测试 | 2 天 |

**优势**：一个后端 = 桌面浏览器 + 手机/平板（局域网）统一入口；严格复用 services（维护成本 = 只有表现层）；数据契约不变，随时可弃。

### 备选：A1 —— VS Code 扩展（先做，零新重量）
如果你想要"今天就能用的 GUI 感"：一个 VS Code 扩展提供侧边栏（anote docs 表格/笔记树/命令面板），后端全调 `anote` CLI。开发量几天，与 B1 不冲突（扩展可以调同一个后端 HTTP API）。

### 明确不建议
- C2 Tkinter（丑）、C4 Electron（8GB 上重）、A2/A3（TEX 短板+数据双轨）、B2 SPA（工程量过大，B1 够用）。

---

## 四、决策建议

**路线**：先 **A1（VS Code 扩展，几天）** 拿到即时 GUI 感 → 再 **B1（Web GUI，2 周）** 作为长期正式 GUI（多端+移动）。
**原则**：无论选哪个，后端一律复用 services；GUI 永远只是"另一个入口"。
